## 3. 关键决策与理由

| 决策 | 理由 | 影响 |
| --- | --- | --- |
| 默认数据库用 H2 文件库，生产用 PostgreSQL | 本机无 Docker/PostgreSQL；H2 文件库数据落盘、重启不丢，且 DDL 保持 PG 兼容子集 | 教师无需安装数据库即可复现；同一套 Flyway 脚本可用于 PG |
| 用 Flyway 版本化迁移替代独立 `schema.sql`/`data.sql` | 一次执行、可重复启动、不丢数据，避免二次启动 DROP 重建 | 文档中说明「建表脚本 = V1，种子数据 = V2」 |
| JWT 不携带权限，每次请求从库加载 | 满足「权限修改后立即生效且不写死」的硬要求 | 每请求多一次用户/权限查询，课程规模可接受 |
| refresh token 存 HttpOnly Cookie + 数据库只存哈希 | 降低 XSS 窃取与数据库泄露风险 | 前端需 `withCredentials`，开发期用 Vite 代理避免跨域 |
| 未配置 `JWT_SIGNING_KEY` 时随机生成 | 仓库不得提交密钥，同时保证开箱即跑 | 重启后旧令牌失效，README 注明生产必须注入固定密钥 |
| 权限矩阵中的业务权限码先全部入库 | 权限目录与角色映射是设计基线，第二/三阶段直接复用 | 第一阶段接口只用身份/组织相关权限码 |

## 8. 同日追加：第一阶段改良与优化（M1.5）

基线可用后做了一轮针对性加固，目标是「把已交付的部分做实」，而不是继续加功能。改动全部有测试或实测证据。

### 8.1 改了什么

| 方向 | 改动 | 理由 |
| --- | --- | --- |
| 认证防护 | 登录失败限流：同一「用户名 + 来源 IP」10 分钟内失败 5 次 → 429，成功登录清零 | 任务书安全项要求防口令枚举；原先只有统一提示，没有频次约束 |
| CSRF 纵深 | `/auth/refresh`、`/auth/logout` 校验 `Origin`/`Referer` 白名单 | 刷新令牌在 Cookie 中，浏览器会自动携带，需要来源校验兜底 |
| 配置安全 | `/h2-console` 仅 `dev` profile 放行，生产 profile 返回 401；frameOptions 同步收紧 | 原先 `permitAll` 对所有 profile 生效，属于配置层面的隐患 |
| 审计闭环 | 新增登录成功/失败、越权访问审计；拒绝事件用 `REQUIRES_NEW` 独立事务落库 | 项目书要求「拒绝事件独立落库」，原先失败路径不写审计 |
| 审计查询 | `GET /api/v1/admin/audit-events`（`audit:read`），按角色收敛作用域（PI 只看本人） | 让审计表从「只写」变成可验证的功能，同时避免横向越权 |
| 列表能力 | 用户/角色列表支持 `sort=field[,asc|desc]` 白名单排序，非法字段 400 | 之前固定按 id 排序，属于已记录的已知限制 |
| 代码质量 | 简化 `UserAdminService.create` 的角色装配，补 `User.register` 集合重载 | 原实现先建再改，语义绕且易错 |
| 前端 | token 改为仅内存保存（刷新页面靠 HttpOnly Cookie 静默换新）；新增审计日志页；用户/角色支持删除；429 友好提示 | 降低 XSS 可读面，补齐后端新能力的演示入口 |
| 质量门禁 | JaCoCo `check`：整体行覆盖率 ≥ 85%、`identity.application` 包 ≥ 80%；GitHub Actions 双 job（后端 verify + 前端 build） | 覆盖率从「写在文档里」变成「CI 里强制」 |
