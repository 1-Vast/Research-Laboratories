# 04 · 接口设计

统一前缀 `/api/v1`，JSON 请求/响应；除注册、登录、刷新外，全部接口要求 `Authorization: Bearer <accessToken>`。

## 1. 返回格式

成功：

```json
{ "code": "OK", "message": "success", "data": { }, "traceId": "9538467fee56472e" }
```

分页数据：

```json
{ "items": [ ], "total": 42, "page": 1, "size": 20 }
```

失败：

```json
{ "code": "VALIDATION_FAILED", "message": "参数校验失败",
  "data": [{ "field": "username", "message": "用户名为 3-32 位字母、数字、下划线、点或短横线" }],
  "traceId": "..." }
```

## 2. 状态码与业务码

| HTTP | 业务码 | 场景 |
| --- | --- | --- |
| 200 | OK | 查询 / 更新成功 |
| 201 | OK | 创建成功（注册、创建用户、创建角色） |
| 204 | — | 删除、退出登录（无正文） |
| 400 | VALIDATION_FAILED / BAD_REQUEST | 参数校验失败、请求体不可解析 |
| 401 | UNAUTHENTICATED / TOKEN_INVALID / TOKEN_EXPIRED / SESSION_REVOKED / ACCOUNT_DISABLED / INVALID_CREDENTIALS | 未认证、令牌无效/过期、会话已注销、账号禁用、登录失败 |
| 403 | FORBIDDEN / PROJECT_MEMBER_REQUIRED / LAB_SCOPE_FORBIDDEN / PROJECT_LEADER_REQUIRED | 无接口权限，或权限够但不在该实验室/项目范围内 |
| 404 | NOT_FOUND / USER_NOT_FOUND / ROLE_NOT_FOUND / PROJECT_NOT_FOUND / TASK_NOT_FOUND / REPORT_NOT_FOUND / LAB_NOT_FOUND | 资源不存在（或隐匿范围） |
| 409 | DUPLICATE_USERNAME / DUPLICATE_ROLE_CODE / LAST_ADMIN_PROTECTED / PROTECTED_ROLE / ROLE_IN_USE / **INVALID_STATE_TRANSITION / VERSION_CONFLICT / DUPLICATE_REPORT_WEEK / OPEN_TASKS_EXIST / PROJECT_NOT_DELETABLE / TASK_NOT_DELETABLE / REPORT_NOT_DELETABLE / SELF_REVIEW_FORBIDDEN** | 唯一约束、状态机非法迁移、乐观锁冲突、业务前置条件不满足 |
| 429 | RATE_LIMITED | 登录失败次数超过阈值（5 次 / 10 分钟） |
| 500 | INTERNAL_ERROR | 兜底，不返回堆栈 |

> **403 与 409 的分工**：403 表示"你没这个资格"（无权限码，或不在作用域内），重试无用；409 表示"你现在做不了这件事"（状态不对、版本过期、前置条件不满足），刷新后重试可能成功。前端据此决定是提示"无权限"还是"请刷新后重试"。
>
> **越权读取返回 403 而非 404**：本项目选择显式拒绝而不是隐匿资源存在性，因为协作场景下成员本就该知道项目存在，返回 404 反而让人困惑。代价是暴露 id 有效性，可接受。

携带 Cookie 的接口（`/auth/refresh`、`/auth/logout`）额外校验 `Origin`/`Referer` 白名单，跨站来源返回 403 `FORBIDDEN`。

## 3. 认证接口

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/v1/auth/register` | 匿名 | 注册；用户名唯一、密码 ≥ 8 位且含字母数字、默认 `RESEARCHER` |
| POST | `/api/v1/auth/login` | 匿名 | 登录；失败统一提示「用户名或密码错误」；下发 HttpOnly 刷新 Cookie |
| POST | `/api/v1/auth/refresh` | 匿名（需 Cookie） | 一次性轮换刷新令牌；重放触发会话吊销 |
| POST | `/api/v1/auth/logout` | 已认证 | 服务端吊销当前会话，清除 Cookie，204 |
| GET | `/api/v1/me` | 已认证 | 当前用户、角色、权限、授权版本 |
| PUT | `/api/v1/me/password` | 已认证 | 自助改密：校验旧密码、策略校验、吊销全部会话（含当前），204 |

登录响应示例：

```json
{
  "code": "OK", "message": "success",
  "data": {
    "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
    "tokenType": "Bearer",
    "expiresIn": 900,
    "user": {
      "id": 4, "username": "researcher_a", "displayName": "苏禾（科研人员A）",
      "enabled": true, "authVersion": 0,
      "roles": [{ "code": "RESEARCHER", "name": "科研人员" }],
      "permissions": ["report:create", "task:read", "..."]
    }
  },
  "traceId": "..."
}
```

`Set-Cookie: labflow_refresh=...; HttpOnly; Path=/api/v1/auth; SameSite=Lax; Max-Age=604800`

## 4. 用户管理（`user:manage`）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/admin/users?keyword=&sort=&page=1&size=20` | 分页 + 关键字（用户名/昵称/邮箱）+ 白名单排序；page ≥ 1，1 ≤ size ≤ 100 |
| GET | `/api/v1/admin/users/{id}` | 详情 |
| POST | `/api/v1/admin/users` | 创建（可指定角色列表，未指定默认 `RESEARCHER`） |
| PATCH | `/api/v1/admin/users/{id}` | 修改昵称/邮箱 |
| PATCH | `/api/v1/admin/users/{id}/enabled` | 启用/禁用；禁用会吊销全部会话并递增 `auth_version` |
| PUT | `/api/v1/admin/users/{id}/roles` | 替换角色集合（至少一个；不可移除最后一个管理员的 `SYS_ADMIN`） |
| DELETE | `/api/v1/admin/users/{id}` | 逻辑删除（禁用并保留历史与审计） |

## 5. 角色与权限管理（`role:manage`）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/admin/roles?keyword=&sort=&page=&size=` | 分页查询 + 白名单排序 |
| GET | `/api/v1/admin/roles/{id}` | 详情（含权限码列表） |
| POST | `/api/v1/admin/roles` | 创建；编码需 `[A-Z][A-Z0-9_]{2,63}` |
| PATCH | `/api/v1/admin/roles/{id}` | 改名/描述；内置角色不可改 |
| DELETE | `/api/v1/admin/roles/{id}` | 删除；内置或被引用返回 409 |
| GET | `/api/v1/admin/permissions` | 权限目录（49 条） |
| PUT | `/api/v1/admin/roles/{id}/permissions` | 替换权限集合；内置管理员角色必须保留 `user:manage`+`role:manage` |
| GET | `/api/v1/admin/audit-events?action=&actorId=&page=&size=` | `audit:read`；脱敏审计记录，按时间倒序；非平台管理员只能看到本人记录 |

排序参数：`sort=field[,asc|desc]`，用户可选 `id,username,displayName,email,enabled,createdAt,updatedAt`，角色可选 `id,code,name,createdAt,updatedAt`；非白名单字段或非法方向返回 400。

## 7. 科研业务接口（已实现）

### 7.1 实验室

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/v1/labs` | `lab:read` | **只返回当前用户所属实验室**，不暴露全平台组织架构 |

返回 `[{id, code, name}]`。前端"新建项目"的实验室下拉用它，用户看不到自己不属于的实验室。

### 7.2 项目

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/v1/projects?labId=&status=&keyword=&sort=&page=&size=` | `project:read` | 只返回本人可见项目（项目成员，或所属实验室的 PI） |
| GET | `/api/v1/projects/{id}` | `project:read` | 返回 `{project, progress, members}` 聚合体 |
| POST | `/api/v1/projects` | `project:create` | 创建草稿，`leaderId` 取当前用户 |
| PUT | `/api/v1/projects/{id}` | `project:update` | 仅负责人、仅 `DRAFT`/`REJECTED` 可改；**不接受 status 字段** |
| DELETE | `/api/v1/projects/{id}` | `project:delete` | 仅负责人、仅 `DRAFT` 可删，否则 409 `PROJECT_NOT_DELETABLE` |
| POST | `/api/v1/projects/{id}/submit` | `project:submit` | `DRAFT`/`REJECTED` → `PENDING` |
| POST | `/api/v1/projects/{id}/approve` | `project:approve` | `PENDING` → `ACTIVE`；PI 且属该实验室；不得批自己的项目 |
| POST | `/api/v1/projects/{id}/reject` | `project:approve` | `PENDING` → `REJECTED`，`reason` 必填 |
| POST | `/api/v1/projects/{id}/reopen` | `project:update` | `REJECTED` → `DRAFT`，改完可再提交 |
| POST | `/api/v1/projects/{id}/close-request` | `project:close-request` | `ACTIVE` → `CLOSING`；存在未完成任务时 409 `OPEN_TASKS_EXIST` |
| POST | `/api/v1/projects/{id}/close-approve` | `project:close-review` | `CLOSING` → `ARCHIVED` |
| POST | `/api/v1/projects/{id}/close-reject` | `project:close-review` | `CLOSING` → `ACTIVE`，`reason` 必填 |
| GET | `/api/v1/projects/{id}/members` | `project:read` | |
| POST | `/api/v1/projects/{id}/members` | `project:member:manage` | 仅负责人；**仅 `ACTIVE`/`CLOSING`**；被加人必须属同实验室 |
| DELETE | `/api/v1/projects/{id}/members/{userId}` | `project:member:manage` | 不能移除负责人本人 |
| GET | `/api/v1/projects/{id}/reviews` | `project:read` | 审批轨迹，按时间正序 |
| GET | `/api/v1/projects/{id}/permissions` | `project:read` | 返回 `{leader, labPi}`，前端据此渲染按钮，**不自行推断 PI 关系** |

所有写操作需带 `version`（`VersionRequest` 或请求体内字段），过期返回 409 `VERSION_CONFLICT`。

### 7.3 任务

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/v1/tasks/mine?status=&page=&size=` | `task:read` | 指派给自己的任务，按 `dueAt` 排序 |
| GET | `/api/v1/projects/{projectId}/tasks?status=&assigneeId=&keyword=` | `task:read` | 需项目成员 |

| GET | `/api/v1/tasks/{id}` | `task:read` | 先反查 `projectId` 再校验成员 |
| PUT | `/api/v1/tasks/{id}` | `task:update` | 仅负责人；`DONE`/`CANCELED` 不可改 |

### 7.4 周报

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/v1/projects/{projectId}/reports?status=&authorId=` | `report:read` | 需项目成员 |
| POST | `/api/v1/projects/{projectId}/reports` | `report:create` | `weekStart` 传任意一天，服务端归一到周一；同周已存在 409 `DUPLICATE_REPORT_WEEK` |
| GET | `/api/v1/reports/{id}` | `report:read` | 先反查 `projectId` 再校验成员 |
| PUT | `/api/v1/reports/{id}` | `report:update` | 仅作者、仅 `DRAFT`/`RETURNED`；**提交后正文只读** |
| DELETE | `/api/v1/reports/{id}` | `report:delete` | 仅 `DRAFT` |
| POST | `/api/v1/reports/{id}/submit` | `report:submit` | `DRAFT`/`RETURNED` → `SUBMITTED` |
| POST | `/api/v1/reports/{id}/review` | `report:review` | `SUBMITTED` → `APPROVED`/`RETURNED`；不得审核自己的周报 |

`taskIds` 里的任务必须属于同一项目，否则 400 `VALIDATION_FAILED`。

### 7.5 三层校验的实际执行顺序

以 `POST /api/v1/tasks/{id}/submit` 为例：

```text
1. JWT 过滤器        → 令牌有效？会话未吊销？账号启用？      → 否则 401
2. @PreAuthorize     → 有 task:submit 权限码？               → 否则 403
3. 反查归属          → 按 taskId 查任务，再查其 projectId     → 不存在 404
4. 项目作用域        → 当前用户是该项目有效成员？            → 否则 403 PROJECT_MEMBER_REQUIRED
5. 领域不变量        → 当前用户是受派人？状态是 IN_PROGRESS？ → 否则 403 / 409
6. 乐观锁            → version 匹配？                        → 否则 409 VERSION_CONFLICT
```

第 3、4 步是防水平越权的关键：**如果只按 `taskId` 直接操作而不反查项目归属，把 URL 里的 id 改成别人的任务就能提交**。`TaskApiTest` 与 `ReportApiTest` 各有一条"越权读取"负例钉住这一点。
