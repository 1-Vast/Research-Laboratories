# 00 · 初步设计总览

> 依据：《期末项目任务书》（V1.0）与《科研实验室智能协同管理平台 · 项目书 V1.1》
> 状态：设计基线（第一阶段已实现并验证，第二、三阶段待实施）

## 1. 项目定位

LabFlow（科研实验室智能协同管理平台）面向高校科研实验室，围绕**项目立项—任务分派—交付验收—周报汇报**的真实科研协作流程，构建一个前后端分离、带持久化数据库、RBAC 权限与完整登录体系的 Web 系统。

解决的核心问题：

| 痛点 | 系统能力 |
| --- | --- |
| 项目推进分散在聊天记录与个人文档 | 项目立项、成员、里程碑与进度 |
| 任务交付标准不一致、缺少验收轨迹 | 任务分派、提交、退回与验收快照 |
| GPU / 工作站靠口头预约，时段冲突 | 资源登记、预约审批、时段冲突约束 |
| 论文笔记与实验结论无法检索复用 | 项目知识条目与成果附件 |
| 人工汇总周报耗时 | 基于授权数据的 AI 周报草稿 |

## 2. 目标用户与角色

题目天然存在 4 类角色，且职责互不相同：

| 角色 | 代码 | 职责 | 授权边界 |
| --- | --- | --- | --- |
| 系统管理员 | `SYS_ADMIN` | 用户、角色、权限、实验室登记、PI 任命 | 管理控制面；默认不读取科研正文 |
| 实验室负责人 | `PI` | 管理实验室成员，审批立项/结项/资源预约 | 仅被任命的实验室 |
| 科研项目负责人 | `PROJECT_LEADER` | 管理所负责项目的成员、任务、周报与成果 | 仅负责人关系的项目 |
| 科研人员 | `RESEARCHER` | 承接任务、提交周报、申请资源、共享成果 | 仅受邀加入的实验室/项目 |

**关键设计**：系统角色决定「具备哪类操作能力」，`lab_members` / `project_members` 决定「在哪个范围具有能力」。两者分离，避免把「项目负责人」当成所有项目的负责人。

## 3. 范围与优先级

| 优先级 | 模块 | 交付内容 | 明确不做 |
| --- | --- | --- | --- |
| P0 | 身份与授权 | 注册、登录、刷新、退出、用户/角色/权限 CRUD、动态授权 | 第三方联邦登录 |
| P0 | 科研项目 | 立项草稿、PI 审批、成员维护、结项归档、分页筛选 | 经费报销、财务审计 |
| P0 | 任务协作 | 分派、开始、提交、退回、验收、进度计算 | 复杂依赖 DAG |
| P0 | 进度汇报 | 周报草稿、提交、审核、退回重提 | 读取私人聊天/邮件 |
| P1 | 资源协同 | 逻辑资源登记、半开区间预约、冲突控制 | 真实 SSH / GPU 排队 |
| P1 | 成果知识 | 成果元数据、附件、知识条目检索 | 真实投稿系统 |
| P1 | 实时与 AI | STOMP 定向通知、授权周报草稿 | 智能体自动审批 |
| P1 | 工程增强 | Redis、MinIO、CI/E2E、审计、Compose | 微服务、K8s |

不纳入本次交付（P2）：RAG、GitHub 同步、资源队列、版本差异对比。

## 4. 交付边界（第一、二阶段已完成）

### 4.1 第一阶段：可运行底座（已完成）

验收标准是可被教师独立复现：

1. 仓库具备 `backend/`、`frontend/`、`docs/` 三段式结构，依赖版本锁定。
2. 数据库迁移脚本一次性建库：RBAC 五表 + 实验室 2 表 + 审计/会话表，共 **10 张表**，四类角色与 5 个演示账号种子数据。
3. 认证闭环：注册（默认最低权限角色）、登录（统一失败提示）、刷新（一次性轮换）、退出（**服务端吊销会话**）、当前用户与权限查询。
4. RBAC 闭环：用户管理（增删改查、启禁用、分配角色）、角色管理（增删改查、分配权限）、权限目录；后端 `@PreAuthorize` 强制校验；权限变更**下一次请求即生效**；最后一个可用管理员受保护。
5. 测试与冒烟：接口级 + 单元 + 真实 PostgreSQL 集成，整体行覆盖率 92.2%；真实 HTTP 走通登录 → 调用接口 → 退出 → 旧令牌 401。

### 4.2 第二阶段：科研业务闭环（已完成）

1. **7 张业务表**（`projects`、`project_members`、`project_reviews`、`tasks`、`task_submissions`、`reports`、`report_tasks`），表总数 17。
2. **三条状态机**：项目（草稿→待审→进行中→结项中→已归档，含驳回与结项退回）、任务（待办→进行中→待验收→已完成，含退回、取消）、周报（草稿→已提交→已通过，含退回重开）。非法迁移一律 409。
3. **36 个业务接口**：项目 17、任务 11、周报 7、实验室 1；全平台共 57 个。
4. **三层授权**：角色给能力、`lab_members` 给实验室范围、`project_members` 给项目范围；按 `taskId`/`reportId` 访问先反查归属，防水平越权。
5. **交付快照不覆盖历史**：退回重提插入新快照行，历史交付内容永久可追溯。
6. **前端 4 个业务页**：项目列表、项目详情（进度/成员/审批轨迹/流转按钮）、我的任务、周报。
7. **验证**：258 个用例全绿、行覆盖率 92.8%、真实 HTTP 端到端 72 项断言全通过、前端 `vue-tsc` + `vite build` 通过。

第三阶段见 [05-实施计划](05-实施计划.md)。

## 5. 验收口径

- 所有权限判断在后端完成，前端隐藏菜单不作为安全手段；
- 越权负例（改 ID、跨项目、无权限、禁用账号、重放令牌）全部有对应测试；
- 每个状态机动作有明确的前置状态与操作者约束，非法跳转返回 409；
- 接口统一返回 `{code, message, data, traceId}`，不向前端抛 Java 堆栈。
